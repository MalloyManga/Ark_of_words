# 小型 Nuxt 网站的安全与高并发入门

## 1. 先建立正确预期

网站安全不是写一个防攻击函数

它是多层防护：

```text
域名和 CDN
→ 云厂商网络防护
→ 防火墙
→ Caddy
→ Nuxt Server API
→ 参数校验
→ 缓存和数据库
→ 日志 监控和备份
```

每一层负责不同问题

业务代码无法独自抵挡大规模 DDoS

但业务代码必须防止攻击者借用我们的服务器攻击别人或读取不该读取的数据

## 2. 当前网站有哪些入口

### 2.1 普通页面

例如：

```text
/
/practice
/practice/session
/operators
```

主要风险是大量请求消耗 SSR CPU 或页面出现 XSS

### 2.2 公开数据 API

```text
/api/operators
/api/operators/:operatorId/voices
/api/health
```

主要风险是恶意刷接口 构造参数和消耗 PRTS 请求额度

### 2.3 PRTS 上游

服务器会请求：

- MediaWiki 语音页面
- 立绘文件信息

用户浏览器会直接请求：

- PRTS 音频静态资源
- 当前实现返回的 PRTS 立绘地址

因此我们既要保护自己的服务器 也要避免给 PRTS 制造不必要压力

### 2.4 未来管理 API

管理 API 可以修改干员和题库配置

它的风险远高于普通读取 API

推荐只通过 Tailscale 私网开放 不直接暴露到公网

## 3. 攻击者可能做什么

## 3.1 枚举和乱填 operatorId

攻击方式：

```text
/api/operators/ines/voices
/api/operators/random-name/voices
/api/operators/../../secret/voices
```

攻击者希望让服务器访问任意页面或文件

当前防护：

- `SupportedOperatorId` 类型限制业务代码
- `isSupportedOperatorId` 在运行时检查 URL 参数
- 白名单外干员返回 404
- PRTS 页面标题从服务端配置读取 不直接相信用户输入

对应风险：

- 路径穿越
- 任意上游请求
- 开放代理
- 缓存键爆炸

## 3.2 SSRF 服务端请求伪造

SSRF 的意思是攻击者诱导我们的服务器访问内网或任意网址

危险例子：

```text
/api/fetch?url=http://127.0.0.1:3000/private
/api/fetch?url=http://169.254.169.254/
```

当前项目没有接受任意 URL 的代理接口

PRTS 请求地址写死在服务端

媒体 URL 还会检查：

- 必须是 HTTPS
- 域名必须属于 PRTS

未来不要增加通用的 `fetch?url=` 接口

如果需要代理音频 必须使用干员和语音白名单映射到固定资源

## 3.3 XSS 跨站脚本

攻击者希望把 JavaScript 塞进页面

例如语音文本中出现：

```html
<script>偷取数据</script>
```

当前 Vue 的 `{{ value }}` 会自动转义 HTML

因此文本只会显示 不会执行

需要长期遵守：

- 不对外部文本使用 `v-html`
- 不把外部字符串拼成脚本
- 不允许用户上传可执行 SVG
- 管理后台预览也必须使用普通文本绑定

## 3.4 Clickjacking 点击劫持

攻击者把我们的网站透明地放进 iframe

再诱导用户点击看不见的按钮

Caddy 已返回：

```text
X-Frame-Options: DENY
```

浏览器会拒绝其他页面嵌入本站

## 3.5 MIME 类型欺骗

攻击者希望浏览器把普通文件当成脚本执行

Caddy 已返回：

```text
X-Content-Type-Options: nosniff
```

浏览器不会随意猜测响应类型

## 3.6 浏览器权限滥用

当前网站不需要摄像头 麦克风和定位

Caddy 已返回：

```text
Permissions-Policy: camera=(), microphone=(), geolocation=()
```

即使未来某段第三方代码尝试调用这些权限 浏览器也会拒绝

## 3.7 刷接口和缓存击穿

攻击者可能同时发起大量相同请求

如果每个请求都穿透到 PRTS 会导致：

- 我们的服务器连接数上升
- PRTS 被重复请求
- 我们的出口 IP 被限流或封禁

当前防护：

- 语音和目录缓存 30 天
- 旧缓存最多继续使用 90 天
- SWR 先返回旧数据再后台更新
- Nitro 在同一进程中合并相同 pending 请求
- 前端标准练习顺序加载干员
- 上游请求 10 秒超时
- 上游请求不自动重试

缓存命中时一千个相同数据请求不等于一千次 PRTS 请求

但是它仍然是一千个到达我们服务器的 HTTP 请求

## 3.8 DDoS 分布式拒绝服务

DDoS 使用大量机器同时消耗带宽和连接

它可能在请求到达 Nuxt 之前就把服务器公网带宽占满

这类问题不能靠 Vue 防抖解决

需要：

- 雨云网络层防护
- Cloudflare CDN 和 DDoS 防护
- 防火墙只开放必要端口
- 合理限流
- 必要时临时封禁来源

没有域名时很难使用完整 Cloudflare 代理

购买域名后可以把 DNS 托管到 Cloudflare 并开启代理

## 3.9 密钥泄露

未来后台会有发布密钥

绝不能放在：

- Vue 组件
- `public/`
- `runtimeConfig.public`
- Git
- LocalStorage
- 浏览器网络请求源码中

密钥应放在本地和雨云的环境变量

更推荐让管理 API 只通过 Tailscale 私网访问

## 3.10 依赖供应链

第三方包可能出现漏洞或恶意版本

当前做法：

- `package-lock.json` 固定实际安装版本
- Docker 使用 `npm ci`
- 依赖数量保持较少

部署前可以检查：

```bash
npm audit
```

不要看到警告就直接执行 `npm audit fix --force`

强制升级可能引入破坏性版本

应先阅读具体漏洞是否影响当前运行路径

## 4. 防抖 节流 缓存和限流的区别

### 防抖 debounce

用户连续触发事件时 只在停止一段时间后执行一次

适合：

- 搜索框
- 自动保存
- 窗口 resize

它不能阻止攻击者绕过页面直接请求 API

### 节流 throttle

一段时间内最多执行一次

适合：

- 鼠标拖动预览
- 滚动事件
- 高频 UI 更新

它同样不是服务器安全机制

### 缓存 cache

相同数据不重复计算或请求上游

适合当前 PRTS 文本和读音

缓存降低计算成本 但不能阻止网络连接本身

### 请求合并 request coalescing

多个相同冷缓存请求只允许第一个访问上游

其余请求等待同一个 Promise

主要防止缓存击穿

### 限流 rate limiting

某个来源超过请求数量后返回 429

它是服务器防滥用机制

但简单按 IP 限流会误伤：

- 学校网络
- 宿舍网络
- 公司网络
- 手机运营商 NAT

这些场景可能有很多用户共享一个公网 IP

因此限流数值应根据真实日志再确定

## 5. 一百人和一千人同时访问会怎样

## 5.1 一百人访问静态页面

Caddy 可以压缩并转发请求

如果页面和 API 缓存已经预热 小型服务器通常有机会承担

但仍取决于：

- CPU
- 内存
- 公网带宽
- SSR 页面耗时
- 用户是否同时加载音频

不能只凭用户数量保证

## 5.2 一百人同时冷启动相同干员

理想流程：

```text
100 个请求
→ Nitro 发现相同缓存键
→ 1 个请求访问 PRTS
→ 其余请求等待
→ 结果写入缓存
→ 100 个请求读取同一结果
```

服务器仍需要维持 100 个连接

但是 PRTS 不应收到 100 次相同请求

## 5.3 一千人同时访问

一台低价 2 核服务器不应承诺稳定承受一千并发

可能出现：

- 连接排队
- SSR 响应变慢
- Node 事件循环延迟
- 内存上涨
- 公网带宽耗尽
- Caddy 或应用超时

推荐路径：

1. 使用域名
2. Cloudflare 代理静态资源和页面
3. 缓存公开 GET API
4. 观察雨云 CPU 内存和流量
5. 根据日志增加限流
6. 必要时升级服务器或拆分服务

学习项目不需要一开始为一千并发付费

先部署 监控 再依据真实数据扩容是正常工程流程

## 6. PRTS 数据和音频流向

当前流程：

```text
用户浏览器
  → 我们的 Nuxt API
  → PRTS MediaWiki API
  → 我们服务器缓存文本 读音 立绘 URL和音频 URL
```

之后：

```text
用户浏览器
  → 我们的 Nuxt API
  → 读取服务器缓存
```

音频播放是：

```text
用户浏览器
  → PRTS 静态音频地址
```

音频字节不经过我们的服务器

立绘当前同样使用 PRTS 返回的媒体 URL

我们的缓存保存的是 URL 而不是图片文件本身

因此向 PRTS 管理员询问时应明确：

- 项目是非商业学习项目
- MediaWiki 文本请求会做长缓存
- 只支持白名单干员
- 不批量扫描全站
- 音频和立绘目前由用户浏览器直连 PRTS 静态资源
- 使用 `preload="none"`
- 是否允许第三方页面直链这些静态资源
- 如果不允许 是否可以自建缓存或对象存储副本

得到答复后再决定最终素材策略

## 7. 部署前检查清单

### 云服务器

- 使用 SSH Key
- 关闭密码登录或使用高强度密码
- 不允许 root 远程密码登录
- 只开放 22 80 443
- 不把 Nuxt 3000 端口暴露公网
- 定期安装系统安全更新

### Docker

- 应用使用非 root 用户
- 不把 Docker Socket 挂入应用容器
- 不把 `.env` 提交到 Git
- 为数据库和缓存配置持久化卷
- 定期备份 SQLite 和重要配置

### 网站

- 配置域名和 HTTPS
- 开启 Cloudflare 代理后确认真实客户端 IP 获取方式
- 检查安全响应头
- 不使用 `v-html` 渲染 PRTS 文本
- 管理 API 不对公网开放
- 对错误响应隐藏内部堆栈和文件路径

### PRTS

- 明确 User-Agent
- 不批量抓取
- 缓存文本和读音
- 遇到 403 429 5xx 不连续重试
- 公开前确认静态音频和立绘直链政策

### 监控

- 查看 Caddy 访问日志
- 查看 Nuxt 错误日志
- 观察 CPU 内存 网络和磁盘
- 关注 403 429 5xx
- 设置服务器磁盘和流量告警

## 8. 出现攻击时怎么办

1. 保存日志 不要先删除证据
2. 判断是单个 IP 滥用还是分布式流量
3. 单个来源可以临时封禁
4. 大流量攻击联系云厂商并开启 CDN 防护
5. 管理密钥泄露立即轮换
6. 检查数据库和配置 revision 是否被修改
7. 从备份恢复前先修复入口
8. 记录事件和改进项

安全的核心不是保证永远不出问题

而是降低攻击成功概率 限制损失范围 并且能够发现和恢复
