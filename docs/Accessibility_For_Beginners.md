# Web 无障碍入门与项目验收指南

## 1. 什么是 Web 无障碍

Web 无障碍通常写作 Accessibility 或 a11y

`a11y` 表示字母 a 和 y 中间省略了 11 个字母

它的目标是让不同能力和不同操作方式的用户都能完成网站核心任务

包括：

- 只使用键盘的用户
- 使用屏幕阅读器的盲人或低视力用户
- 难以分辨低对比颜色的用户
- 容易被剧烈动画影响的用户
- 临时受伤无法使用鼠标的用户
- 在小屏幕或高倍缩放下使用网站的用户

无障碍不是额外制作一套网站

它是让现有 HTML 结构 状态和交互表达得更清楚

## 2. WCAG 的四个原则

WCAG 是常用的 Web 无障碍标准

可以先记住 POUR：

### Perceivable 可感知

用户能感知内容

例如：

- 图片有替代文本
- 文字和背景对比足够
- 状态不只通过颜色表达
- 加载和完成状态能被屏幕阅读器听到

### Operable 可操作

用户能操作页面

例如：

- 所有按钮都能用键盘到达
- Tab 顺序合理
- Modal 不会让焦点跑到背景
- Esc 可以关闭覆盖层
- 动画不会造成不适

### Understandable 可理解

用户能理解页面和错误

例如：

- 按钮文字描述真实行为
- 相同操作在不同页面保持一致
- 错误信息说明发生了什么和怎么恢复
- 输入模式提示不会只显示一个红框

### Robust 健壮

辅助技术能够理解页面

例如：

- 优先使用原生 button a main h1
- ARIA 属性与实际状态一致
- HTML 结构合法
- 不用 div 模拟按钮

## 3. 当前项目已经实现什么

## 3.1 原生语义元素

主要交互使用：

- `button`
- `a` 或 `NuxtLink`
- `main`
- `header`
- `section`
- `aside`
- 标题元素

原生元素自带键盘行为和辅助技术语义

这比给普通 div 添加 click 事件可靠

## 3.2 跳到主要内容

页面首个键盘焦点是：

```text
跳到主要内容
```

它平时移出屏幕 获得焦点后显示

按 Enter 后跳过重复导航 直接进入当前页面 main

实现位置：

```text
app/components/AppSkipLink.vue
app/app.vue
```

每个页面的主要区域使用相同 ID：

```html
<main id="main-content" tabindex="-1">
```

## 3.3 可见键盘焦点

全局为链接 按钮 输入框和 tabindex 元素提供：

- 白天模式蓝色轮廓
- 夜间模式青色轮廓
- 与元素保持间距

鼠标点击不会强制显示轮廓

键盘导航时使用 `:focus-visible` 显示

实现位置：

```text
app/assets/css/main.css
```

## 3.4 Modal 和抽屉焦点锁定

覆盖层打开时：

1. 记录当前触发按钮
2. 等待 Vue 渲染覆盖层
3. 聚焦第一个可操作控件
4. Tab 在覆盖层内部向前循环
5. Shift + Tab 在内部向后循环
6. Esc 关闭覆盖层
7. 关闭后焦点回到原触发按钮

实现位置：

```text
app/composables/useOverlayFocusTrap.ts
```

已用于：

- 输入法提示 Modal
- 练习池 Modal
- 干员语音抽屉
- 已选语音抽屉

覆盖层使用：

```html
role="dialog"
aria-modal="true"
aria-labelledby="标题 ID"
```

## 3.5 动态状态播报

加载面板使用：

```html
aria-live="polite"
aria-busy="true"
role="progressbar"
aria-valuenow
```

屏幕阅读器可以知道页面正在加载以及当前进度

练习完成面板也使用 `aria-live="polite"`

## 3.6 减少动态效果

操作系统开启 Reduce Motion 后：

- 动画时长缩短
- Transition 时长缩短
- 连续动画只执行一次
- 平滑滚动关闭

检测方式：

```css
@media (prefers-reduced-motion: reduce)
```

它不会要求用户在网站里再找一个独立开关

网站尊重操作系统偏好

## 4. 键盘测试方法

测试时先把鼠标放到一边

每个页面都执行以下步骤

### 4.1 首页

1. 刷新页面
2. 按一次 Tab
3. 确认出现“跳到主要内容”
4. 按 Enter
5. 确认焦点跳到主要内容
6. 继续按 Tab
7. 确认导航链接和主题按钮都有清晰轮廓
8. 使用 Enter 激活链接和按钮

### 4.2 难度页面

1. 确认返回按钮可聚焦
2. 确认每个难度卡片可聚焦
3. 使用 Enter 进入练习
4. 检查焦点顺序是否和视觉顺序一致

### 4.3 干员页面

1. 使用 Tab 到达每张干员卡片
2. 使用 Enter 打开干员语音抽屉
3. 继续按 Tab 确认焦点不会进入背景干员卡片
4. 使用 Shift + Tab 检查反向循环
5. 按 Esc 关闭
6. 确认焦点回到刚才的干员卡片
7. 打开右上角已选语音
8. 测试单删 清空和关闭按钮

### 4.4 练习页面

1. 检查返回按钮和工具栏
2. 打开练习池 Modal
3. 检查 Tab 是否锁定在 Modal 中
4. 使用 Esc 关闭
5. 完成一组练习
6. 确认“换一组”和“再次练习”都能使用键盘

## 5. Windows 屏幕阅读器测试

## 5.1 Narrator 讲述人

Windows 自带 Narrator

常用启动快捷键：

```text
Win + Ctrl + Enter
```

测试重点：

- 页面标题是否合理
- 按钮是否读出名称
- 干员卡片是否读出干员名
- Modal 打开后是否读出标题
- 加载时是否读出忙碌状态
- 完成时是否读出完成提示
- 删除按钮是否读出具体删除哪条语音

## 5.2 NVDA

NVDA 是 Windows 上常用的免费屏幕阅读器

建议正式上线前安装并完成一次主流程测试

测试路径：

```text
首页
→ 难度选择
→ 五题练习
→ 完成页面
→ 干员自由配置
→ 已选语音抽屉
```

不要只检查“它会发声”

需要判断读出的名称和顺序是否能让用户理解当前操作

## 6. Lighthouse 自动检查

Chrome DevTools 中：

1. 打开 Lighthouse
2. 只勾选 Accessibility
3. 分别检查手机和桌面模式
4. 生成报告
5. 逐项阅读失败原因

Lighthouse 擅长发现：

- 缺少 label
- 图片缺少 alt
- 对比度不足
- ARIA 属性错误
- 标题顺序问题
- 小部分键盘问题

Lighthouse 无法可靠判断：

- 焦点顺序是否符合业务逻辑
- Modal 是否真的好用
- 屏幕阅读器播报是否容易理解
- 按钮文字是否符合用户预期
- 完整练习流程是否只用键盘完成

自动得分高不等于无障碍完成

## 7. 颜色和对比度

普通文字建议达到至少 4.5:1

大号文字建议达到至少 3:1

可以使用 Chrome DevTools 颜色选择器查看对比度

需要分别检查：

- 白天模式
- 夜间模式
- 按钮正常状态
- Hover 状态
- Focus 状态
- Disabled 状态
- 正确 错误 额外和待输入字符

状态不能只靠颜色

例如未来可以为错误状态增加屏幕阅读器文本或错误数量

## 8. 图片和图标

内容图片需要有描述性 alt

例如干员立绘：

```html
alt="伊内丝 portrait"
```

纯装饰图片使用：

```html
alt=""
```

图标按钮必须有可读名称：

```html
<button aria-label="关闭已选语音">
```

不能指望屏幕阅读器理解 SVG 路径长什么样

## 9. 当前仍需人工验证的项目

代码完成不代表最终验收完成

部署前仍需检查：

- 所有视口下焦点轮廓没有被裁切
- Modal 中动态新增按钮后焦点循环仍正确
- 主题切换后的颜色对比度
- 浏览器 200% 缩放下页面仍可操作
- 手机横屏和窄屏下抽屉内容不会丢失
- Narrator 或 NVDA 完整主流程
- Lighthouse 手机和桌面报告
- 自动播放失败时是否有可理解的手动恢复方式

项目当前隐藏所有滚动条

这不会阻止滚轮和触摸滚动 但会降低“这里可以滚动”的视觉提示

如果实际测试中用户无法发现可滚动区域 应重新评估全局隐藏滚动条的设计

## 10. 推荐验收顺序

每次新增页面或复杂交互后：

1. Type Check
2. 只用键盘跑主流程
3. 检查焦点打开和关闭位置
4. 检查白天和夜间对比度
5. 开启 Reduce Motion
6. 浏览器缩放到 200%
7. Lighthouse
8. Narrator 或 NVDA

无障碍最有效的做法不是开发结束后一次补完

而是把这些检查加入每个模块的验收流程
